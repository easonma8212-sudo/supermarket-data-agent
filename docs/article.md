# 从零理解企业数据 Agent：从可信指标到可执行决策

**面试准备稿｜2026 年 9 月**

企业数据 Agent 的目标不是把自然语言翻译成一条 SQL，而是把业务问题转成可授权、可复核的分析任务，再把结果交付给合适的人。以“这个月营收为什么没达标”为例，系统至少要知道“营收”的口径、月的时区、目标版本、用户可见范围、数据是否更新完毕，以及“为什么”究竟是在问算术贡献还是因果机制。少了其中任何一项，流畅的回答都可能误导决策。

本文从零解释一套可落地的设计，并用仓库中的虚构数据最小实现验证关键边界。文中“建议架构”是设计方案；“已实现”仅指这个仓库中通过测试的示例能力；所有阿里国际业务名词都作为**面试场景假设**，不代表对其内部系统或真实指标口径的了解。

## 一、先把问题定义清楚

普通 BI 看板以图表为中心：人选择指标、过滤器，再自行解释。数据 Agent 以任务为中心：人提出问题，系统负责澄清、选择受治理的指标、运行分析、交付结论并保留证据。如果系统还要主动发早报或异常提醒，就必须再管理订阅、接收者、审批和降噪。

这个岗位截图中的职责可归纳为六件事：设计交互与能力、建立质量标准、配置 Skill 和工作流、形成反馈闭环、定义 IM 与看板等下游场景、支持专题分析。把六件事堆给一个大模型并不能构成产品。大模型擅长解释含糊意图和生成文字；指标口径、权限、数值计算、数据时效及发送动作要由确定性服务管理。[NIST AI 风险管理框架](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)也强调：系统应在接近部署条件下被测试，并在运行后持续监测。

### 一个具体问题如何出错

用户问：“德国市场昨天 GMV 为什么下降？”系统若直接检索表结构并生成 SQL，可能面临四种不同错误。第一，GMV 究竟按下单、支付还是退款后净额统计，数据库字段名不会自动说明。第二，“昨天”要按哪个市场的自然日计算。第三，用户是否有权查看德国市场或明细。第四，即使德国市场下降与某渠道流量下降同时发生，相关变化也不等于因果证明。可信回答需要逐步排除这些错误，而不是只检查 SQL 能否执行。

## 二、先建数据契约，再谈 Agent

### 认证指标是什么

认证指标是经过负责人确认、能够被版本化复用的业务计算定义。一个可用的指标条目至少包含：名称、公式、单位、时间粒度、维度、过滤规则、时区、数据时效、生效日期、负责人和废弃规则。语义层把这些定义组织成模型，让多个消费端使用同一套计算规则。以 [dbt Semantic Layer 的 MetricFlow 设计](https://www.getdbt.com/blog/how-the-dbt-semantic-layer-works)为例，模型可根据语义模型中的实体关系构造连接路径并生成查询 SQL。它减少了每次提问临时解释指标的机会，却不能保证指标定义本身永远正确；认证和变更仍需要业务与数据负责人共同治理。

用户说“营收”时，Agent 应先识别可能对应的认证指标。若存在“支付金额”和“退款后净额”两个合理候选，正确动作是澄清。选定后，工具请求传入指标名、版本、日期范围与过滤器，由指标服务编译查询。只有在治理覆盖不足的长尾探索中，才考虑受限的 SQL 路径，并额外进行只读、表列白名单、扫描预算和人工审阅。

### 权限与模型上下文是两道门

第一道门决定用户可查询哪些记录和字段。数据平台通常通过行级与列级策略实现这件事；[BigQuery 行级安全](https://docs.cloud.google.com/bigquery/docs/row-level-security-intro)和[列级访问控制](https://docs.cloud.google.com/bigquery/docs/column-level-security-intro)是可参考的实现方式。第二道门决定查询结果中哪些内容可以进入模型上下文，哪些只能以聚合或遮蔽形式展示。即使查询本身被授权，也不能自动推论整张明细表适合送入模型。OWASP 将敏感信息泄露列为 LLM 应用风险，建议限制数据来源和实行最小权限。[OWASP 敏感信息披露说明](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/)。

跨区域数据处理还需要按具体数据类型、传输路径、合同和适用法规确定控制措施。本文只提出工程上可配置的区域边界和审计记录，不给任何地区的法律问题作统一结论。

### 数据时效决定能不能分析

一次查询应同时返回数值和元数据：查询 ID、指标版本、时间窗、过滤器、数据更新时间、缺失状态与来源。数据未更新时，不能把缺数解释成零，更不能据此发“下降”提醒。频繁且稳定的查询可以采用预聚合或物化视图，但是否提高性能要在真实负载下测量；[BigQuery 物化视图文档](https://docs.cloud.google.com/bigquery/docs/materialized-views-intro)说明了预计算对重复查询的用途及新鲜度机制。

## 三、一次请求的完整执行过程

```text
提问或订阅事件
  → 身份、场景与权限校验
  → 意图识别；歧义时澄清
  → 确定性工作流或有限步骤规划
  → 认证指标查询与数据质量检查
  → 统计计算、维度变化分解
  → 有证据的文字叙述
  → 数字与引用校验
  → 如需外发或写入，进入审批和投递门
  → 日志、评测与反馈
```

**路由**的核心是识别问题类型：取数、比较、解释、预测、知识问答或操作请求。频率高且步骤固定的需求，例如管理者日报，适合版本化工作流；需要多次下钻的探索问题，可以由规划器制定有限步骤的查询计划。这个分流是一种工程取舍，取决于场景覆盖率、时延、成本和错误代价，不应说成业界对所有系统的统一结论。

**Skill**应是带明确输入输出契约的可调用能力，例如 `query_metric(metric, time_range, filters)`、`decompose_change(metric, dimension, periods)`、`draft_summary(evidence)`。Skill 的配置需要版本、依赖、超时、失败返回和权限要求。MCP（Model Context Protocol）可以让宿主应用以标准方式发现和调用工具；[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)定义了工具及其 schema。但 MCP 本身并不替业务系统完成行级授权、审计、限流或指标治理。[MCP 授权规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)说明，授权能力及具体传输方式还取决于实现。

**受限规划器**只提交意图和参数，不获得无限制数据库与发送权限。服务端根据用户身份重新校验每一步；设置最大工具次数、最大扫描量、超时和停止条件。外部文档、工具返回和用户输入都不能升级成系统指令。OWASP 的[提示注入](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)与[过度自主性](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)条目分别说明了这两类风险。

## 四、如何正确解释“为什么下降”

“变化分解”与“根因”需要分开。假设某指标前一天合计 300 美元，后一天 290 美元，其中德国市场从 100 降到 80，美国市场从 200 升到 210。那么总变化是 -10 美元；德国贡献 -20 美元，美国贡献 +10 美元，两项相加与总变化一致。可严谨地说“德国市场的下降在算术上抵消了美国市场的增长，并使总额净下降 10 美元”。不能据此断言“德国流量质量下降导致了结果”，因为尚未检查流量、转化、客单价、活动、订单状态和数据管道。

仓库的 [`demo/data_agent.py`](../demo/data_agent.py)正是这样做的：只查询一个认证的演示指标，先核查市场权限和日批完成状态，再对两个相同筛选范围的日期做分解；维度合计不能对齐总变化时直接报错。它特意把结论标成“算术贡献，不证明因果关系”。这条边界比生成一段听起来合理的解释更有价值。

如果要做真正的异常检测，应先定义业务周期、基线与阈值，并用历史数据回放测量误报和漏报。STL 是将时间序列分为趋势、季节性和剩余项的方法，本身并不是“超过 3σ 就一定异常”的通用规则，见 [Forecasting: Principles and Practice 的 STL 章节](https://otexts.com/fpp3/stl.html)。预测也需要在训练数据之外检验，并展示区间或不确定性，而不只给一个点值，见该书的[预测准确性](https://otexts.com/fpp3/accuracy.html)与[预测区间](https://otexts.com/fpp3/prediction-intervals.html)章节。

## 五、从答案到主动触达

同一分析核心可以支持对话、看板旁的解释、定时报表与异动提醒，但四种入口的风险不同。用户主动发问时，系统只需把答案返回给当前用户；主动触达时，系统必须确认接收者、订阅目的、数据授权、消息有效期和发送频率。对高影响通知，先形成可预览草稿并由负责人员放行。审批应由服务端实施，不能只在提示词中写“请先征求同意”。

提醒的成功标准也不只是“发出去”：要量化真正有效的事件占比、重复通知率、误报率、打开后的行动率，以及用户退订率。每条消息都应带来源与时间戳，让接收者能知道数字何时更新、按什么口径计算。若后续更正了指标，系统还要能定位此前已发送的消息并决定是否补发纠错。

## 六、质量度量要拆到每一步

“准确率”不是一个万能数字。可将端到端任务拆成：意图是否理解、指标是否选对、权限是否执行、查询结果是否正确、分解是否对账、文字是否忠于证据、是否在约定时延内交付。对于 Text to SQL，SQL 文本相同与否无法完全说明结果是否正确，因此应按执行结果和业务口径评测；[Spider 原始论文](https://yale-lily.github.io/public/seq2sql_dataset_emnlp2018.pdf)是这类任务评测的基础参考，但企业评测集还须包含自己的权限、口径和时区边界。

离线评测集应由业务与数据负责人共同标注，并按场景保留版本。至少包括：同义词、歧义问题、跨时区、缺数、基期为零、越权访问、错误工具返回、统计分解、模型叙述错误。发布前运行固定回归集；上线后抽样复核真实会话及投诉。对于开放式解释，可让模型辅助初筛，但应定期与人类标注比对，不能把模型评分当唯一真值。NIST 要求记录测试集、测量方法及接近部署条件的系统表现，并在运行中监测组件行为，见其[Measure 指南](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)。

质量报告至少同时给出**分母、样本来源、时间范围和置信边界**。例如“最近两周，在 120 个预先冻结的管理者取数样例中，认证指标选择正确 114 个”，比单说“准确率 95%”更可核查。时延应报告 P50 与 P95、超时率和工作流完成率；业务价值可看实际使用、决策采纳及省下的人工分析时间，但必须排除仅因新鲜感产生的短期使用。

## 七、自迭代是治理流程，不是模型自己变好

一次差评可能指向五类问题：意图理解错误、指标定义错误、源数据缺失、分析方法不当、叙述夸大。系统先记录复现材料，再由负责人判定归属，选择修口径、修数据、调整工作流、补工具能力或改写提示词。修复后的案例加入评测集，回归通过才发布。高频、稳定的问题可以固化为工作流；新的业务结论则需经过审核才能成为知识库内容。

这个闭环的关键资产不是“bad case 数量”，而是可以复现的测试、明确的归因标签和可追溯的版本。这样才能回答：“上一次改动改善了什么，有没有破坏别的场景？”

## 八、0 到 1 如何落地

第一阶段应选一个口径清楚、用户明确、错误代价可控的任务。例如“查询一个认证指标，并按市场解释它相对上一日的变化”。先定义指标与权限，准备少量真实但脱敏的历史样例，跑通查询、证据链和维度对账。本文仓库的最小实现就是这个阶段的教学版本，使用虚构订单数据；它**不包含 LLM、真实数据库、MCP 或消息发送**。

第二阶段接入一个真实入口，增加澄清、会话上下文与工作流配置；建立 50 至 100 个由业务方核对的黄金样例作为起点，并记录每次失败。样例数量是项目启动建议，不是可靠性结论。第三阶段在误报率、权限测试和审批流程达到约定门槛后，才开放主动提醒。长尾探索、预测、多入口统一和自动知识沉淀依次扩展，每一步都以可测的业务收益决定是否继续。

面试中可以用一句话概括这套架构：“我会先用认证指标和服务端权限把数字做对，用受限的工作流与 Agent 把问题答清，再用评测、审批和反馈把主动触达做稳。”随后举一个自己**确实做过**的项目，讲明你负责哪一环、如何定义质量、上线后看到了什么证据。原架构文档中的个人履历表未经核实，不应作为你的面试事实。
