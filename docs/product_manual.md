# 超市 Data Agent 产品手册

本手册采用追加式版本记录。新决策、新功能和架构调整写入新的版本章节；已经发布的历史章节不回写、不覆盖。事实错误需要在新版本中用“更正”条目说明。

## v0.1.0：数据源调查与试点定位（2026-09-20）

### 产品定位

建立一个只读的超市经营 Data Agent。首版从 POS 导出文件读取数据，不连接 POS 底层数据库，不修改线上记录。

### 已确认的数据

- 销售明细：2026-06-29 至 2026-09-20，共 8,223 行。
- 正常商品库存快照：2026-09-20，共 4,378 行。
- 文件格式：GB18030 编码、TAB 分隔，首列表头含 HTML，末尾有空列。
- 销售导出主动排除了会员卡号、会员名称和备注。

### 初始架构思路

1. POS 网页负责业务操作和人工导出。
2. 本机 PostgreSQL 保存导出副本和分析结果。
3. Data Agent 只查询本机数据库。
4. 首版不向 POS 写回数据，也不自动发送采购单。

### 初始风险判断

库存导出中没有正库存记录，因此最初把库存异常检测列为首要能力，并暂停自动补货设想。

## v0.2.0：销售优先与本地数据底座（2026-09-20）

### 决策变化

用户确认 POS 主要用于记账，未用于可靠的库存管理。负库存不代表实际门店库存异常。产品路线调整如下：

- 库存异常检测从首版主功能中移除。
- 补货建议主要根据历史销售速度生成。
- POS 库存仅作为可选参考，不作为阻断条件或真实库存承诺。
- 继续保留数据质量能力，但优先检查销售数据完整性、重复导入、字段缺失和日期覆盖。

### 本版本范围

- 创建独立 PostgreSQL 数据库 `supermarket_agent`。
- 建立 `ops`、`raw`、`analytics` 三层结构。
- 导入 12 周销售明细和商品/库存快照。
- 提供每日销售与商品销售两个只读汇总视图。
- 建立可重复执行、可追踪来源文件哈希的导入流程。

### 暂不确定的补货参数

正式生成补货数量前，需要用户确认：

- 建议覆盖多少天销量；
- 供应商通常几天到货；
- 是否存在整箱规格或最小订货量；
- 生鲜与包装商品是否使用不同规则；
- 特价拼单等虚拟货号是否应排除。

在这些口径确定前，系统可以先给出商品日均销量、销售频次和建议关注清单，但不把结果描述为最终订货数量。

### 安全边界

- 数据库和 Agent 均为本机运行。
- 原始业务文件不提交到 Git。
- 不导入会员身份字段。
- 不写回 POS，不自动下单。

## v0.2.1：首次导入完成（2026-09-20）

### 实施结果

- `supermarket_agent` 数据库已在本机 PostgreSQL 14.18 中建立。
- 成功导入 8,223 行销售明细，覆盖 2026-06-29 至 2026-09-20，共 84 个自然日。
- 成功导入 4,378 行商品/库存快照，快照日期为 2026-09-20。
- 两个来源文件共登记 12,601 行，文件名、SHA-256 和导入时间记录在 `ops.import_run`。
- 当前 84 天实际销售金额合计为 65,704.00 元，涉及 4,654 个按日去重的小票。
- 相同文件重复导入后，销售和商品行数保持不变，确认不会重复累加。

### 导入兼容性记录

实际 POS 导出与网页显示存在两项格式差异：

- 日期可能使用 `2026/9/20 13:08:06`，也可能使用 `2026-09-20 13:08:06`。
- 折扣率可能使用半角 `%` 或全角 `％`。

导入器现已兼容两种日期分隔符和两种百分号，并增加自动测试。

### 当前可查询的数据产品

- `analytics.daily_sales`：每日销售金额、销量、小票数、明细行数和客单价。
- `analytics.product_sales`：商品累计销量、销售金额、销售频次、首末销售日和平均售价。

### 下一版本目标

定义首版“补货关注清单”的业务口径。下一版先输出可解释的销售速度和建议覆盖量，不自动生成采购单，也不使用 POS 负库存作为必需条件。

## v0.3.0：补货关注清单（2026-09-20）

### 新增能力

新增 `analytics.replenishment_attention` 只读视图。视图使用最近 28 个自然日销量估算未来覆盖期需求，并显示前后两个 28 天周期的销量趋势。

### 采购渠道规则

- 饮料、酒水、农夫水、礼盒奶和零食暂归为本地供应商补货，默认覆盖期为 7 天。
- 日化、家居百货和文具类暂归为自行采购，同时计算 30 天和 60 天需求情景。
- 其他分类进入待人工分类，不计算补货覆盖量。

### 口径说明

本版本的数值名称为“预计覆盖需求”，不是“建议订货量”。计算不扣除库存、不包含在途采购，也不替代人工查看货架和库房。

### 数据分类限制

系统中有 571 个产生过销售的商品仍属于“预置类”。仅凭该分类无法确定供应渠道，因此本版本不按商品名称关键词擅自分类。后续可通过人工维护商品到采购渠道的映射逐步解决。

### 架构变化

- 新增 `config` 数据库 schema，存放可调整的补货策略和类别映射。
- 采购覆盖天数从分析 SQL 中分离到 `config.replenishment_policy`。
- 类别与采购方式映射存放在 `config.category_supply_mode`，以后可以逐项修订，不必修改 Agent 代码。

## v0.3.1：路线更正，补货功能降为可选（2026-09-20）

### 更正原因

上一版本把用户提出的“可以根据销售情况做推荐补货建议”理解成了当前主线，并进一步提出清理采购渠道分类。用户确认补货不是前期主要内容，采购渠道分类也不是当前必须完成的工作。

### 当前产品主线

产品恢复为以下优先级：

1. 只读经营分析：回答销售额、销量、商品、类别、日期和趋势问题。
2. 销售数据质量：检查重复导入、日期覆盖、缺失商品编号、异常金额和数据新鲜度。
3. 自然语言查询：让用户直接用中文询问经营情况，并返回数据范围和计算依据。
4. 日报或周报：在用户确认指标后再建立。

### 补货能力的处理

- `analytics.replenishment_attention` 保留为实验性、可选视图，避免删除已经完成的可逆工作。
- 暂停采购渠道分类、订货参数和补货流程建设。
- 该视图不进入首版 Agent 的默认工具、回答流程或主要界面。
- 只有用户以后明确把补货列为目标时，才重新评估这条支线。

### 下一阶段

建立经营分析的认证指标口径和查询服务。优先从每日销售额、订单数、客单价、销量、畅销商品、滞销商品和类别趋势开始。

## v0.4.0：首版中文经营问答（2026-09-20）

### 用户确认的问题范围

首版围绕五类日常经营问题：

1. 今日、昨日和本周销售额。
2. 畅销商品。
3. 商品销售上升或下降。
4. 类别销售贡献。
5. 客单价和订单量变化。

### 实现方式

本版本使用确定性的中文意图匹配和固定 SQL，不调用外部大模型。相同问题在相同数据上得到相同结果，便于逐项核对指标和建立信任。

### 认证指标口径

- 销售额：销售明细中“实际金额”之和。
- 销售数量：销售明细中“数量”之和，保留称重商品小数。
- 小票数：按销售单号去重。
- 客单价：同期销售额除以同期去重小票数。
- 类别贡献：类别销售额除以同期全部销售额。
- 商品销售变化：最近完整 7 天销售额与此前完整 7 天销售额之差。

指标定义存放在 `config.metric_definition`，避免口径散落在提示词或回答文本中。

### 数据完整性规则

当前导出文件最新记录为 2026-09-20 中午，因此最新日期不是完整营业日。本版本采用保守规则：

- “今日”回答可以展示最新日期，但必须标记为部分日。
- 趋势、畅销商品和类别贡献使用最新数据日期的前一天作为完整日截止日期。
- 每个回答必须展示数据覆盖范围和最新记录时间。

### 当前边界

- 暂不支持任意自由问题、追问上下文或同义词无限扩展。
- 暂不生成图表、日报或外部通知。
- 暂不对销售变化作因果解释，只陈述可核对的算术变化。

## v0.4.1：商品趋势口径更正（2026-09-20）

### 发现的问题

端到端验证发现，用户问题是“哪些商品销量明显上升或下降”，v0.4.0 的实现却按商品销售额变化排序。销售额会同时受到价格和数量影响，不能替代销量。

### 更正

- 商品趋势改为比较最近完整 7 天销售数量与此前完整 7 天销售数量。
- 排名和回答均使用数量差，不再显示为金额差。
- 畅销商品榜仍默认按销售额排序，并在回答标题中明确注明。
- 不对变化给出原因推断。

## v0.4.2：企业级 Data Agent 架构适配评估（2026-09-20）

### 评估结论

《阿里国际-数据Agent架构推演》适合作为本项目的长期设计原则，但不适合按照企业级规模整套照搬。超市当前只有单店、本机 PostgreSQL、人工导出的 POS 数据和少量固定经营问题，应采用压缩后的渐进式架构。

### 当前保留的原则

- 优先建设认证指标和语义口径，不让指标定义散落在提示词里。
- 高频、口径固定的问题优先使用确定性 Workflow；自由规划型 Agent 后置。
- 每个回答携带数据覆盖范围、新鲜度和计算依据，保证结果可核对。
- 通过固定测试问题和预期答案逐步建立 Golden Set，并在每次变更后回归。
- 继续保持只读、最小数据范围、本机运行和不写回 POS 的边界。

### 暂不引入的企业级组件

- MCP Server、多个 Agent 自由协商和复杂 Planner/Reflection 框架。
- Flink、湖仓、实时流式计算和高并发物化体系。
- 多租户行列权限、跨国家数据驻留和复杂组织权限。
- 自动异常告警、主动消息触达、自动采购或其他写回动作。
- 在缺少明确需求和评估样本前引入预测、GraphRAG、向量检索等能力。

### 适合超市的简化目标架构

1. 数据接入层：继续接收 POS 导出文件，后续再判断是否值得自动同步。
2. 数据与指标层：本机 PostgreSQL、原始表、分析视图、认证指标和数据新鲜度。
3. 分析能力层：先维护五类固定经营问答，再逐步增加受约束的自由查询和多步分析。
4. 使用界面层：当前使用终端；指标稳定后再增加本地网页对话或日报。
5. 横向保障：自动测试、Golden Set、证据展示、隐私边界和人工确认。

### 与当前实现的对应关系

- 数据层已有真实 POS 数据和本机数据库。
- 语义层已有首批认证指标与完整日规则。
- 能力层已有五类确定性经营问答。
- 编排层目前只有轻量意图路由，尚无 Planner、Memory 和 Reflection。
- 交互层目前只有终端入口。
- 质量体系已有单元测试，下一步应补真实经营问题的 Golden Set。

### 路线决定

下一步不扩建补货、异常检测或企业级基础设施，而是先建立首批真实问题 Golden Set，并验证现有五类问答的口径、覆盖和失败提示。只有固定问答稳定后，才引入有限的自然语言理解和对话上下文。

## v0.5.0：首批经营问答 Golden Set（2026-09-20）

### 新增评估资产

- 建立包含 30 个真实中文表达的版本化 Golden Set。
- 五类已支持问题各包含一个真实数据基准案例和四个自然语言变体。
- 加入库存、补货、利润、原因分析和未来预测五类越界问题。
- 记录当前数据快照的日期范围、最新时间、完整日和销售明细行数。

### 回归方式

- 普通模式检查全部 30 个问题是否路由到正确能力，不连接数据库。
- `--live` 模式连接本机 PostgreSQL，并核对五个基准问题的关键答案片段。
- 数据快照变化时，真实数据回归主动失败，避免在没有人工核对的情况下自动接受新答案。

### 本次发现与修正

- “这周生意怎么样”现在可以识别为销售概览。
- 补充营业额、商品销售排行、前后两周对比、品类占比等常见表达。
- 修正“销售额最高的商品”和“商品销售排行”被误分为销售概览的问题。
- 对利润、库存、补货、原因和预测问题明确提示超出范围，不用其他指标替代回答，也不访问数据库。

### 验证结果

- 30 个 Golden Set 问题全部通过意图路由验证。
- 5 个基准问题全部通过真实数据库答案验证。
- 项目自动测试共 16 项，全部通过。

### 当前定位

系统已经从“能运行的固定问答”进入“有第一版可回归质量基线的固定问答”。它仍不是可以任意自由提问的完整 Data Agent，但以后每次扩展同义表达、指标或分析能力，都可以用相同基线检查是否引入退化。

## v0.6.0：本机网页聊天界面（2026-09-20）

### 用户入口变化

- 新增浏览器聊天界面，用户不再需要为每个经营问题执行命令行命令。
- 页面打开后直接显示聊天工作区、数据库连接状态、数据覆盖范围和五个示例问题。
- 支持输入问题、Enter 发送、Shift + Enter 换行、点击示例问题和清空当前对话。
- 对话历史只保存在当前浏览器页面，刷新或关闭后清空。

### 技术结构

- 新增本机 Python HTTP 服务，提供静态页面、`/api/status` 和 `/api/chat`。
- `/api/chat` 直接复用 `app/sales_agent.py`，网页和命令行使用同一套指标、路由和回答逻辑。
- 前端使用独立的 HTML、CSS 和 JavaScript，不引入新的外部运行依赖。
- 服务默认只监听 `127.0.0.1:8765`，不向局域网或互联网开放。

### 数据与安全边界

- 继续只读访问本机 PostgreSQL。
- 不写回 POS，不执行采购，不发送外部消息。
- 页面不需要登录，因为只能从当前电脑访问；如果以后开放到其他设备，必须先增加身份认证和访问控制。
- 用户问题限制为 500 字，请求体限制为 16 KB。
- 数据库不可用或查询失败时，页面显示明确错误，不伪造经营答案。

### 验证结果

- 页面、状态接口和聊天接口均能从本机访问。
- 网页问题“这周生意怎么样”能够返回真实销售数据。
- 网页问题“哪些类别贡献最多”能够返回真实类别贡献结果。
- 发送、清空对话、数据库状态和窄屏布局已经过浏览器验证。
- 项目自动测试增加到 19 项，全部通过。

### 当前限制

- 网页服务需要用户在本机启动，尚未设置为开机自动运行。
- 当前仍是单轮问题路由；页面显示多轮消息，但系统尚不会理解“再看看上周”这类依赖上文的追问。
- 当前没有远程访问、用户账号或云端部署。

## v0.6.1：AI API 介入时机与合格 Data Agent 路线（2026-09-20）

### 产品定位

本项目的近期目标定义为“单店、只读、经营分析型 Data Agent”。合格标准不是拥有多 Agent、MCP 或自动执行能力，而是能够可靠理解日常经营问题，调用受控数据工具，返回可核对结果，并在问题超出能力时明确说明。

### AI API 介入原则

- AI 不直接连接数据库，不生成并执行任意 SQL。
- AI 负责识别意图、提取日期和排序等参数、选择受控分析工具、组织自然语言答案。
- 认证指标、日期口径、权限、SQL 和数值计算继续由本机程序负责。
- 传给 API 的内容尽量限制为用户问题、工具定义和必要的汇总结果，不发送整份销售明细。
- API 密钥只能保存在本机服务端环境中，不能写进网页 JavaScript 或提交到代码仓库。

### 分阶段路线

#### v0.7：参数化分析工具，不接 AI

- 将固定问答重构为带明确参数的工具：日期范围、对比周期、Top N、销售额或销量排序、商品或类别筛选。
- 为每个工具定义输入、输出、错误和证据结构。
- Golden Set 扩展到至少 60 个问题，并加入边界日期、空数据和歧义问题。

#### v0.8：AI 理解与工具调用

- 通过 AI API 将自然语言转换成严格的工具名称和参数。
- 只允许调用白名单只读工具；不允许模型提交 SQL。
- 首先使用影子模式：同时运行规则路由和 AI 路由，记录差异但仍以确定性结果为准。
- Golden Set 达到约定准确率后，才让 AI 成为默认理解层；规则路由继续作为降级路径。

#### v0.9：多轮上下文与解释

- 支持“再看上周”“改成按销量”“只看饮料”等追问。
- 对歧义问题先澄清，不擅自选择日期、指标或排序方式。
- 回答同时返回指标口径、查询期间、数据截止时间和所调用工具。

#### v1.0：可靠运行

- 记录请求、工具调用、耗时、错误类型和用户反馈，但不记录不必要的敏感数据。
- 对 API 超时、限流、数据库不可用和无数据建立降级提示。
- 建立成本上限、每日调用量统计、版本回归和可回退机制。
- 通过一段时间的真实使用验证问题覆盖率、答案正确率和实际经营价值。

### 合格标准

1. 理解：能覆盖大多数真实经营问法，并正确处理时间、指标、筛选和排序。
2. 可靠：所有数字来自认证工具，相同输入和数据得到一致结果。
3. 可解释：回答显示数据范围、指标口径和证据，不虚构原因。
4. 安全：只读、工具白名单、参数校验、密钥不进入浏览器。
5. 对话：能够处理必要的追问和歧义澄清。
6. 评估：变更前后运行 Golden Set，错误案例进入回归集。
7. 运维：API 或数据库失败时可诊断、可降级、可恢复。

### 非必要条件

以下能力不是首个合格版本的前置条件：多 Agent 协商、MCP Server、向量数据库、自动异常推送、预测模型、自动采购和自动写回业务系统。它们只有在出现明确业务收益时再评估。

## v0.7.1：路线更正，LLM 提前承担语言理解（2026-09-20）

### 更正原因

上一版本计划继续为“最近30天”“前5名”“按销量”“只看饮料”等表达建立确定性解析。用户指出，这些正是 LLM 应直接理解的内容；如果继续为大量自然语言变体编写规则，会重复建设语言模型已经具备的能力，也会拖延真正的 Agent 化。

### 路线调整

- 不再以穷举关键词和自然语言规则作为 v0.7 的主要建设方向。
- 已完成的五个参数化工具和严格参数校验保持不变，它们是 LLM 的安全执行边界。
- 下一步提前进入 AI API 影子模式，让 LLM 负责选择工具和填写参数。
- 当前确定性路由只保留为降级路径和对照基线，不继续扩展成复杂自然语言解析器。
- Golden Set 的扩展重点从“同义词是否命中规则”改为“LLM 是否选择正确工具、参数是否正确、是否应该澄清”。

### 不需要澄清的情况

1. 用户已经明确给出指标、时间、筛选或排序，例如“最近30天销售额”“前5名按销量排序”“只看饮料”。
2. 缺少的参数存在已公布且风险较低的默认值，例如“畅销商品”默认最近完整7天、按销售额、前10名；回答中必须展示默认口径。
3. 可以同时展示多个解释且成本很低，例如“卖得最好”可以默认按销售额回答，同时附带销量。
4. 数据最新一天不完整，但仍可安全回答；系统直接回答并标记“部分日”，不要求用户确认。

### 必须澄清的情况

只有当缺失信息会造成两个或多个明显不同、且没有安全默认值的答案时才澄清。例如：

- “和以前比怎么样”：没有说明比较哪个期间。
- “这个商品怎么样”：当前对话中没有明确商品，或名称匹配到多个商品。
- “帮我看看经营情况”：用户想看的指标范围过宽，并且没有已经约定的经营概览模板。
- 同一句话中的条件互相冲突，例如同时要求按销售额和按销量作为唯一排序。

每次最多询问一个最关键的问题，不把参数表交给用户填写。

### 不属于澄清的情况

- 数据库没有利润数据：直接说明暂不支持利润分析，不追问措辞。
- 请求库存异常或补货：直接说明当前版本未开放该能力。
- 要求解释销售下降原因：先说明当前只能展示相关商品或类别的算术贡献，不能证明因果；可以提供已有分析，不把推断包装成原因。
- API 或数据库故障：报告系统状态并降级，不向用户询问业务问题。

### 决策顺序

1. 能直接映射到白名单工具和合法参数：执行。
2. 缺少参数但有明确默认值：使用默认值，并在答案中说明。
3. 可以低成本展示多个口径：同时展示，避免打断用户。
4. 缺失关键参数且不同解释会显著改变答案：澄清一次。
5. 数据不存在或能力未开放：明确说明边界，不进行无意义澄清。

### 下一步

下一版本直接建设 AI API 影子模式：LLM 只生成工具调用，不直接查询数据库。首批评估集将同时标注期望工具、期望参数和“执行、使用默认值、澄清、拒答”四种决策类型。

- 新增 `evals/ai_shadow_golden_set.json`，包含 10 个真实影子案例。
- 新增 `scripts/evaluate_ai_shadow.py`，逐项调用真实模型并严格比较期望决策、工具和完整参数。
- 评估覆盖明确参数、默认口径、固定日期、类别筛选、两期 KPI 对比、商品下降、类别贡献、必须澄清、库存拒答和利润拒答。
- 支持 `--case` 只运行指定案例、`--json` 输出结构化结果、`--repeat` 重复运行以检测同一问题的决策漂移。
- 每项结果都明确记录 `tool_executed: false`；整个评估器没有调用经营数据库工具的代码路径。

### 第一轮真实结果

首次完整评估通过 8/10：

- “最近两周客单价和小票数对比”虽然选择了正确工具，但把两个7天期间整体向前错移了一周。
- “和以前比怎么样”同时缺少指标和期间，模型却自行选择 KPI 对比，没有按产品政策澄清。

这两个失败说明：严格 Function Calling 可以约束模型只能使用白名单工具，但不能仅凭工具结构保证业务决策和日期口径正确，仍然需要版本化评估和明确政策。

### 第一次校准及不稳定性发现

规划政策增加两条通用规则：最近两周对比必须以最新完整日为截止；缺少比较指标和期间时必须澄清。两个失败案例单独复测一度达到 2/2，但随后完整回归只有 9/10，“和以前比怎么样”再次被错误执行。

这证明单次成功不能视为稳定通过，同一模型在相同输入上仍可能出现决策漂移。因此没有把中间结果记录为完成状态。

### 稳定性措施

- 将“比较请求缺少比较对象时必须澄清”提升为执行前硬门禁，明确禁止自行选择 KPI 工具。
- 将模型采样温度设置为 0，减少非必要输出漂移。
- 为评估器增加重复运行能力，不再只看单次正确率。
- 批量重复测试期间发现一次远端连接被主动断开；API 客户端增加最多3次的有限短退避重试。
- 仅对超时、断连、限流和常见服务端临时错误重试；非临时 HTTP 错误不会被掩盖。
- 重试耗尽后转换为可记录的单案例错误，避免整批评估因一次瞬时连接问题直接崩溃。

### 最终验证

## v1.0.0-alpha：第一版通用 NL2Metrics 语义层（2026-09-20）

### 为什么优先 NL2Metrics，而不是直接 NL2SQL

NL2SQL 允许模型自由决定表、字段、连接、聚合和子查询，覆盖范围更广，但也更容易产生错表、重复连接、指标口径漂移、慢查询或访问不应开放的字段。生成的 SQL 即使语法正确，也不代表业务含义正确。

NL2Metrics 让模型只表达受控业务语义：指标、维度、筛选、时间、对比、排序和数量限制；固定程序再把语义计划编译成参数化 SQL。这样可以在扩大自然语言覆盖范围的同时，保持指标口径和数据库权限稳定。

先积累 NL2Metrics 无法覆盖的真实探索性问题，是为了识别用户真正需要的自由度。如果缺口主要是新指标、新维度或常见交叉分析，应优先扩展语义层；只有大量问题确实需要临时跨表连接、复杂子查询或未建模字段时，才考虑在独立只读账号、语法树校验、表字段白名单、成本限制和查询超时下开放受限 NL2SQL。

### 新增通用语义计划

新增 `query_metrics` 工具，包含以下结构：

- 指标：销售额、销量、小票数、客单价、平均售价。
- 单一维度：商品、类别、日期，或不分组汇总。
- 筛选：具体商品名称/编号、类别。
- 时间：明确起止日期，控制是否允许最新部分日。
- 对比：无对比或紧邻此前等长期间。
- 输出：认证指标排序、升降序、最多50行。

LLM 生成的是这一语义计划，不生成 SQL。所有字段均使用严格结构，额外字段不被接受。

### 商品实体解析

- 用户可以直接说“鸡蛋”，不需要知道商品编号。
- 程序先在本机按商品编号或完整商品名称精确匹配，再进行包含匹配。
- 唯一匹配后转换成稳定的 `item_no`，指标 SQL 只使用商品编号筛选。
- 多个匹配时列出最多5个候选并要求用户指定，不让模型自行选择。
- 没有匹配时要求提供更完整名称或编号。
- 商品文本始终作为 PostgreSQL 参数传递，不拼接进 SQL。

真实数据中，“鸡蛋”唯一解析为商品编号 `00110`；“牛奶”匹配多个具体商品，系统会列出蒙牛纯牛奶、伊利纯牛奶、金典、旺仔牛奶等候选并澄清。

### 确定性 SQL 编译器

新增 `app/metric_query.py`：

- 只从认证指标表达式和维度表达式中选择 SQL 片段。
- 用户输入只能进入参数变量，不能成为 SQL 结构。
- 日期不能超出已导入数据范围，默认不能超过最新完整日。
- 排序指标必须同时出现在查询指标中。
- 每次最多返回50行。
- 前期对比自动计算紧邻的等长日期范围。
- 日期趋势没有排行要求时，编译器自动返回请求范围内的完整天数，避免模型错误地只返回一天。

### 与旧工具的关系

当前是渐进式迁移，不是立即删除全部专用工具：

- 指定商品汇总、商品日趋势、商品前期对比和普通指标组合优先使用 `query_metrics`。
- “哪些商品上升/下降最多”暂时继续使用商品差值排行工具。
- 类别销售贡献率暂时继续使用类别贡献专用工具。

后两类涉及跨期差值排序和窗口占比，后续在通用语义层明确建模后再迁移，避免为了形式统一降低计算可靠性。

### 指标目录

新增 `docs/metric_catalog.md`，记录每个指标的固定计算口径、维度、筛选、时间规则、排序限制和未开放范围。该目录是 NL2Metrics 的业务契约，不由提示词临时决定。

### 真实端到端验证

1. “鸡蛋最近30天卖得怎么样”：解析为 `query_metrics`，商品 `00110`，返回销售额、销量、小票数、客单价和平均售价；校准后不再擅自增加前期对比。
2. “鸡蛋最近7天每天销量是多少”：解析日期维度并完整返回7天。首次发现模型把 `limit` 设为1，随后由确定性编译器增加“无排行时覆盖完整期间”的规范化规则。
3. “鸡蛋最近7天和此前7天的销售额对比”：正确返回 2026-09-13 至 2026-09-19 与 2026-09-06 至 2026-09-12 两个等长期间。
4. “牛奶最近7天销售额是多少”：匹配多个商品，返回候选澄清，未执行主指标查询。

集成过程中还发现 NL2Metrics 结果结构与旧模板结构不同，旧模板在分发前提前读取 `rows` 导致网页返回通用错误。已调整模板分发顺序并新增专门回归测试。

### 评估与测试

- 新增 `evals/nl2metrics_golden_set.json`，首批覆盖商品概览、日趋势和前期对比。
- 三个真实 LLM 规划案例 3/3 通过。
- 本地自动测试增加到 49 项，全部通过。
- 网页仍显示实际工具、校验状态和是否执行本机查询。

### 当前限制

- 每次只支持一个维度，尚不支持“商品×日期”“类别×日期”等二维结果。
- 前期对比只支持紧邻等长期间，不支持同比、节假日对齐或用户指定两个任意期间。
- 商品实体解析使用精确和包含匹配，尚未使用别名词典、条码纠错或向量检索。
- 多商品候选澄清仍是单轮，用户需要下一次输入完整商品名称或编号。
- 商品差值排行和类别贡献率仍使用专用工具。
- 利润、毛利、可靠库存、补货、会员、供应商、采购和任意 SQL 未开放。

### 下一步

先让用户在网页用真实商品和经营问题测试，收集商品别名、类别名称、二维分析和时间对比方面的失败案例。下一版优先建设多轮澄清上下文和商品别名映射；随后再评估二维维度与差值指标是否应纳入通用语义层。受限 NL2SQL 继续作为真实探索性缺口积累后的候选能力，不提前开放。

## v1.1.0-alpha：本机多轮语义上下文（2026-09-20）

### 本版本目标

让用户可以在网页中基于上一轮查询继续补充或修改条件，而不必每次重复完整的商品、指标和日期描述。多轮能力只延续语义计划，不把数据库结果交给 LLM。

### 核心原则

- LLM 仍然不生成 SQL；它生成或修改 NL2Metrics 语义计划。
- SQL 继续由本机确定性编译器生成。
- 上下文不包含销售明细、查询结果或最终经营数字。
- 商品候选选择优先由本机程序确定，不让 LLM 猜测“第一个”对应哪个商品。
- 点击清空对话或重启服务后，上下文重置。

### 浏览器会话

- 浏览器使用 `crypto.randomUUID()` 生成随机会话编号，并保存在当前标签页的 `sessionStorage`。
- 每次 `/api/chat` 请求携带 `conversationId`。
- 服务端只接受长度和字符集合法的会话编号。
- 点击“清空对话”时立即生成新编号，旧上下文不再被后续请求使用。
- 页面回答状态会显示“已使用上一轮上下文”。

### 本机上下文存储

新增 `app/conversation_store.py`：

- 状态只保存在网页服务内存，不写入数据库或日志文件。
- 最多保存100个本机会话。
- 会话超过1小时未使用后自动过期。
- 存入和读取时使用深拷贝，避免请求之间意外共享可变对象。
- 服务重启后全部状态自然清空。

### 保存的上下文内容

- 上一轮用户问题。
- 上一轮决策类型。
- 上一个成功的工具名和语义参数。
- 待澄清时的澄清问题。
- 商品实体解析产生的候选商品编号、名称和类别。

不保存或发送数据库结果行、销售金额、销量、小票数或其他经营结果。

### 两种续接路径

#### 确定性商品候选续接

当商品名称匹配多个商品时，程序保存原始 NL2Metrics 参数和候选列表。下一轮支持：

- “第一个”“第二个”等中文序号。
- `1`、`2` 等数字序号。
- 完整商品名称。
- 商品编号。
- 能唯一匹配某个候选的名称片段。

匹配成功后，程序把原计划中的 `product_query` 替换为选中商品编号并直接执行，不再调用 LLM 重新解释整个问题。

#### LLM 语义计划续接

普通追问会把上一轮问题和语义计划作为 `conversation_context` 提供给规划器。模型继承当前问题没有修改的商品、指标、维度和时间，只应用本轮明确变化。例如：

- 上一轮查鸡蛋，下一轮“改成最近7天”保留鸡蛋。
- “每天看销量”把维度改为日期、指标改为销量。
- “再和此前7天比”保留其他条件并增加等长前期对比。

### 真实端到端验收

第一组：

1. “牛奶最近7天销售额是多少”返回5个具体候选，未执行主指标查询。
2. 同一会话回复“第一个”。
3. 程序选择“蒙牛纯牛奶250ml*24瓶（6923644210151）”，继承最近7天和销售额指标，成功返回结果。
4. 第二轮 `contextUsed: true`，且候选选择没有再次调用 LLM。

第二组：

1. “鸡蛋最近30天卖得怎么样”返回鸡蛋30天指标。
2. 同一会话回复“改成最近7天每天看销量”。
3. LLM 保留商品 `鸡蛋`，将期间修改为 2026-09-13 至 2026-09-19、维度修改为 `day`、指标修改为 `sales_quantity`。
4. 编译器规范化为7行，最终完整返回7天销量；第二轮 `contextUsed: true`。

### 测试结果

- 新增候选序号续接、上下文载荷、会话深拷贝、过期清理和浏览器会话测试。
- 本地自动测试增加到55项，全部通过。
- 网页服务已重新启动并加载多轮版本。

### 当前限制

- 只保存最近一个成功语义计划，不是完整长对话记忆。
- 服务重启后上下文丢失，这是当前本机 MVP 的预期行为。
- 浏览器会话编号用于隔离本机标签页，不是用户身份认证；系统仍只允许监听 `127.0.0.1`。
- 不能追问依赖上一轮实际数值的计算，例如“刚才第一名占总额多少”，因为查询结果没有发送给 LLM。
- 多候选名称片段如果仍匹配多个商品，会继续需要更明确的选择。

### 下一步

由用户在网页重点测试省略表达，例如“改成7天”“按天看”“再和上周比”“换成第二个商品”。将失败案例加入多轮 Golden Set；稳定后再决定是否需要持久化对话、结果引用或二维指标，而不是立即保存完整聊天和经营结果。

## v1.2.0-alpha：经营概览与变化拆解 Skill（2026-09-20）

### 架构与实际范围

新增项目内 `skills/business-review/SKILL.md`，说明适用问题、期间规则、分析步骤和因果边界。规划器加载该说明，并可选择 `run_business_review`。执行器在 `app/business_review.py`，完成固定的多步经营分析流程；没有安装成全局 Codex Skill。

用户问全店“最近一周生意怎么样”“销售变化体现在哪些类别和商品”时，LLM 选择 Skill 和期间。普通问数、指定商品查询继续使用 NL2Metrics。首版只接受当前1至31个完整日，与紧邻此前等长期间比较，不能省略用户指定的商品或类别筛选而转为全店分析。

### 数据和证据

读取日期覆盖后，依次执行两期核心指标汇总、全部类别金额拆分、全部商品金额拆分。三项分析查询均使用只读事务和10秒数据库超时。先全量计算差额并对账，再选择增加和减少各前3项，列出剩余项净变化；不会用各期 Top N 代替全量拆分。

报告以 E1 核心指标、E2 类别变化、E3 商品变化组织证据。类别和商品是两种独立拆分，不可相加；此前金额为0或负值时不输出增长率；无交易日期提示核实停业或漏导。缺失金额、商品编号、小票编号时暂停经营结论；拆分与总额不符时阻止报告。

这些检查只覆盖已导入数据，不证明 POS 导出绝对完整，也不等于全面数据质量审计。数据刷新期间三项查询尚未使用跨查询的同一个快照；如金额不一致会对账失败。

### 方法边界与隐私

首版为 LLM 选择 Skill + 固定程序组织查询和报告，不是 LLM 根据结果自主决定下一步的分析循环。汇总结果与销售明细仍留在本机，没有新增向模型发送经营结果的路径。修改 Skill 文字不会自动修改计算方法，需要同步更新 Python 执行器和测试。

报告只定位变化体现在哪里，不认定促销、缺货、天气或客流原因。小票数不等于人数。另校正商品/类别过滤或分组时的客单价展示名称为“每张相关小票的所选商品金额”，避免误解为整单消费金额；指标公式不变。

### 验证与测试入口

58项自动测试通过，包括日期覆盖、零基数、缺失记录提示及对账不一致拦截。真实本机两期数据：2026-09-13 至 2026-09-19 对比此前7天，销售额净增加804.70元，两种拆分合计分别与全店一致。

真实网页通过“最近一周生意怎么样？帮我分析变化体现在哪些类别和商品”自动选择 Skill，并通过“改成最近14天”续接。新增规划评估集 `evals/business_review_golden_set.json`。网页新增“经营分析报告”按钮，原问数和多轮能力继续保留。

### 下一步

收集实际报告反馈，扩展分析评估（单品问题不能丢失筛选、数据不足拒绝、增长/下降前提核验）。若需要模型基于结果灵活追查，再设计受控聚合证据输入和有调用预算的分析循环，并明确更新隐私范围；目前不声称具备该能力。

## v1.3.0-alpha：网页图文经营报告（2026-09-20）

### 产品思路与展示

根据用户反馈，将经营分析 Skill 的长文字结果升级为聊天内嵌 HTML 报告。顶部显示分析期间、对比期间和一句话销售变化结论；三张指标卡展示销售额、小票数、全店客单价及此前值和变化率。类别与商品分别展示增减各前三项的双向条形图，保留其余项净变化与全店对账说明。

完整类别和商品数据表按需展开；原文字证据与口径也可展开查看。图表不单靠颜色区分方向，同时提供左右位置、正负号和金额。窄屏指标卡改为纵向排列，长商品名换行，明细表可滚动。普通问数仍以原文字输出，并非所有查询均已图表化。

### 架构与边界

`run_business_review` 在原文字之外返回结构化 `report`，经运行时与本机网页接口传到新增的 `web/report.js`、`web/report.css`。图文共享同一份本机查询结果，后端以 Decimal 对账，金额精度以字符串传递，前端数值转换仅用于显示与绘图。未添加外部图表依赖，业务名称按文本节点插入。

数据字段检查失败时不生成图表；金额拆分对账失败仍阻止分析。缺失交易日期的提示同时显示在报告中。零或负基数不展示增长率，无有效小票时不计算客单价。报告说明变化体现在哪里，不证明原因；类别和商品拆分不能相加。

此次仅扩展展示层，不改变 LLM 选择 Skill、固定程序查询和组织证据的架构；没有向模型发送经营结果，也没有新增数据库写入、独立报告归档或 PDF 导出。页面刷新后不保留报告，需重新生成。

### 验证与使用

59项自动测试通过，新增结构化报告 JSON 序列化、金额字符串保留、缺失日期提示和异常数据隐藏图表的检查。真实网页点击“经营分析报告”生成2026-09-13至2026-09-19报告，销售额5,568.50元，较此前增加804.70元；浏览器确认指标、类别与商品图表正常显示。

打开本机网页，点击“经营分析报告”，或者输入“最近一周生意怎么样？帮我分析销售变化主要体现在哪些类别和商品”。后续可继续追问调整期间。下一步先收集阅读反馈，再决定是否增加独立报告页面、趋势图和导出功能。

## v1.3.1-planning：五层架构与超市项目对应关系（2026-09-21）

### 定位结论

《阿里国际-数据Agent架构推演》的五层架构可以用于本项目，但应按单店、本机、只读的边界缩小实施。当前产品已经跑通“网页提问 → LLM 选择受控能力 → 语义计划校验 → PostgreSQL 只读查询 → 固定程序生成文字或图文报告”的最小闭环。它对应完整架构中的一条纵向切片，不等于五层已经建设完成。

### 五层对应

触达层目前是本机网页 Chatbot 和内嵌图文经营报告，尚无独立报告库、定时早报、异常提醒和微信等外部渠道。近期先完善网页报告与报告历史；主动触达应在数据自动更新、误报率和人工审核机制稳定后再做。

编排层目前由 OpenAI 模型完成问题理解、澄清和单个工具选择，本机运行时校验参数、执行一个批准的工具，并保存一小时内的语义上下文。尚无多 Skill 执行 DAG、调用预算、执行后反思和 Workflow 与探索 Agent 的完整双模调度。下一阶段增加受限的多 Skill 编排，限制步骤、工具和终止条件；受限 NL2SQL 只用于语义层长期覆盖不了的探索问题。

能力层目前包括通用 NL2Metrics、销售专用查询工具和经营概览与变化拆解 Skill。Skill 仍由代码和说明文件共同实现，并非可视化配置，也未通过 MCP 对外提供。近期依次补充销售趋势、商品表现、品类结构、数据质量和节假日前后分析，并统一输入、证据、失败条件和输出契约。本机单体阶段不为形式统一而提前引入 MCP。

语义层目前认证销售额、销量、小票数、全店客单价和平均售价，限制允许的维度、筛选、比较、排序和日期范围，再由确定性编译器生成参数化 SQL。经营报告还执行字段完整性和全店差额对账。尚缺指标版本、生效日期、负责人、变更审批、真实用户权限、查询 ID 和完整证据链；利润、毛利、可信库存、会员与采购指标仍不开放。

数据层目前使用本机 PostgreSQL，保存 POS 销售与库存导出副本、导入批次和哈希，提供分析视图与数据新鲜度口径。销售查询是只读的，库存数据不作为可靠补货依据。尚缺自动增量同步、导入监控、备份恢复、性能预算和高频查询物化；应先解决稳定导入与可观测性，再按真实性能瓶颈优化。

### 两条纵切系统

质量度量已具备自动测试、不同能力的 Golden Set、安全参数校验、零基数和金额对账等基础，但尚未形成意图、选能力、参数、执行、解释各环节的独立准确率看板，也没有发布门禁和真实用户任务完成率。

自迭代目前依赖用户测试反馈、失败案例人工整理、追加式产品日志和回归测试。尚无点赞点踩、失败会话采集、Bad Case 自动分类和评测集半自动沉淀。自迭代的目标是形成“反馈 → 人工归因 → 修改 Skill、语义或编排 → 加入回归集 → 发布”的治理闭环，不是让模型自行修改生产逻辑。

### 推荐实施顺序

第一阶段继续完善能力层和质量度量：先做销售趋势 Skill、商品表现 Skill，并为每项能力加入 Golden Set 和确定性校验。第二阶段建设有限多 Skill 编排，让一个经营问题最多调用两至三个能力并合并证据。第三阶段补数据自动更新、报告历史和反馈入口。第四阶段根据真实未覆盖问题决定是否引入受限 NL2SQL。主动提醒、外部渠道、权限体系和 MCP 服务化放在需要多人使用或远程部署时再建设。
