## 重要发现

- 商品档案页面显示 4,379 条商品；“正常状态”库存查询导出 4,378 条，说明约有 1 条商品处于其他状态或未被该过滤条件覆盖。
- 4,378 条正常商品中，3,459 条库存为负数，919 条为零，正库存为 0。
- 商品档案直接导出被平台权限策略阻止。没有绕过权限；库存查询导出已覆盖货号、条码、名称、规格、单位、成本、库存上下限、类别和品牌，可作为试点的商品维表来源。

因此，首版 Agent 不应自动生成或执行补货单。应先把“负库存”作为数据质量问题确认：它可能代表系统中的销售扣减方向、期初库存未录入、仓库范围不完整，或历史盘点/入库数据未同步。

## PostgreSQL 建议

本机已有 PostgreSQL 14.18，运行在 `127.0.0.1:5432`。试点无需安装第二套数据库服务，建议在现有实例中新建独立逻辑数据库 `supermarket_agent`，与已有数据库隔离。

建议的最小表：

- `raw_sales_detail`：原始销售明细落地表
- `raw_inventory_snapshot`：每日库存快照
- `dim_product`：从库存导出构建的商品维表
- `fact_sales`：清洗后的销售事实表
- `data_quality_issue`：异常库存、缺条码、重复商品等问题
- `agent_run`：每次分析的输入范围、结果和时间

数据库只保存导出的副本；首版不连接或写回 POS 生产数据库。

## 首版 Agent 范围

首版定位为“只读经营分析 + 数据质量 Agent”：

1. 自动导入销售和库存导出文件。
2. 生成日销售额、销量、毛利估算、畅销/滞销商品和分类趋势。
3. 检测负库存、零库存、缺失条码、重复货号和异常价格。
4. 用自然语言回答“昨天卖得最好是什么”“哪些商品连续有销售但库存异常”等问题。
5. 所有建议附带数据时间范围和依据，不自动修改 POS。

## 后续数据

若要做可靠的补货建议，还需要：

- 至少 8–12 周销售明细，用于星期效应和需求趋势；
- 采购/入库明细及供应商字段；
- 仓库和门店范围说明；
- 负库存业务含义及期初库存确认；
- 退货、调拨和盘点数据（若这些动作不在销售/库存导出中完整反映）。

## 实施顺序

1. 建立 `supermarket_agent` 数据库及只读导入脚本。
2. 标准化当前三份 CSV，并写入原始层。
3. 生成数据质量报告，先解释负库存来源。
4. 上线一个只读问答与日报原型。
5. 数据质量稳定后，再评估补货建议；任何写回 POS 的能力另行审批和隔离测试。
